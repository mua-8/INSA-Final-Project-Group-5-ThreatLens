## 1. Overview & Architecture

Module B provides the persistent storage, relational integrity, and RESTful API layer that connects all ThreatLens modules:
- **Module A (Muaz):** Sends parsed events to the storage layer via `/api/ingest`.
- **Module C (Yamlak):** Receives events and outputs alerts with linked evidence events, which are persisted into SQLite.
- **Module D (Sabri):** Consumes `/api/statistics`, `/api/events`, `/api/alerts`, and `/api/incidents` to power the SOC Dashboard and Investigation screens.

```
       [Raw Logs]
           │
           ▼
   [Module A: Parser]
           │ (events)
           ▼
┌───────────────────────── Module B (Adnan) ─────────────────────────┐
│                                                                   │
│  Flask REST API  ◄─────────►  Repository Layer (Parameterized)    │
│  (/api/ingest, events,        │                                   │
│   alerts, incidents,          ▼                                   │
│   statistics)          SQLite Database (6 Normalized Tables)      │
│                               │                                   │
└───────────────────────────────┼───────────────────────────────────┘
                                ▲
                                │ (correlated alerts + evidence)
                     [Module C: Detection Engine]
                                │
                                ▼
                     [Module D: SOC Dashboard]
```

## 2. Database Schema (SQLite)

The database enforces foreign key constraints (`PRAGMA foreign_keys = ON;`) and WAL journal mode (`PRAGMA journal_mode = WAL;`) for high concurrency.

### Table 1: `log_files`
Tracks uploaded log files and prevents duplicate submissions.
| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Unique log file ID |
| `filename` | TEXT | NOT NULL | Original filename |
| `file_hash` | TEXT | NOT NULL UNIQUE | SHA-256 hash of raw file content |
| `uploaded_at` | TEXT | NOT NULL DEFAULT (UTC) | Ingestion timestamp |
| `line_count` | INTEGER | NOT NULL DEFAULT 0 | Total lines in file |
| `event_count` | INTEGER | NOT NULL DEFAULT 0 | Total parsed events extracted |
| `malformed_count` | INTEGER | NOT NULL DEFAULT 0 | Count of malformed/unparseable lines |

### Table 2: `events`
Structured representation of SSH authentication log entries.
| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Event ID |
| `log_file_id` | INTEGER | NOT NULL, FK -> `log_files(id)` ON DELETE CASCADE | Parent log file |
| `timestamp` | TEXT | NOT NULL | ISO-8601 formatted event time |
| `host` | TEXT | NULLABLE | Target hostname/server name |
| `username` | TEXT | NULLABLE | Attempted username |
| `source_ip` | TEXT | NULLABLE | Remote IP address |
| `port` | INTEGER | NULLABLE | Remote source port |
| `method` | TEXT | NULLABLE | Auth method (e.g., `password`, `publickey`) |
| `outcome` | TEXT | NOT NULL CHECK in (`success`, `failure`, `unknown`) | Outcome |
| `event_type` | TEXT | NOT NULL | e.g. `failed_login`, `accepted_login`, `invalid_user` |
| `raw_line` | TEXT | NOT NULL | Original unparsed log line for forensics |
| `line_hash` | TEXT | NOT NULL | Hash of log line for deduplication |
| *Constraint* | - | UNIQUE(`log_file_id`, `line_hash`) | Prevents duplicate event lines |

*Indexes:* `idx_events_source_ip`, `idx_events_timestamp`, `idx_events_username`.

### Table 3: `alerts`
Security alerts generated by the Detection Engine (Module C).
| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Alert ID |
| `rule_id` | TEXT | NOT NULL | Rule code: `DR-01`, `DR-02`, `DR-03`, `DR-04`, `DR-05` |
| `rule_name` | TEXT | NOT NULL | Human-readable rule title |
| `severity` | TEXT | NOT NULL CHECK in (`low`, `medium`, `high`, `critical`) | Threat level |
| `status` | TEXT | NOT NULL DEFAULT `new` CHECK in (`new`, `investigating`, `resolved`, `false_positive`) | Analyst triage status |
| `source_ip` | TEXT | NOT NULL | Attacking source IP address |
| `first_seen` | TEXT | NOT NULL | Start timestamp of triggering attack window |
| `last_seen` | TEXT | NOT NULL | Latest timestamp of triggering attack window |
| `summary` | TEXT | NOT NULL | One-line analyst synopsis |
| `explanation` | TEXT | NOT NULL | Human-readable explanation with thresholds |
| `settings` | TEXT | NOT NULL DEFAULT '{}' | JSON blob of detection parameters applied |
| `created_at` | TEXT | NOT NULL DEFAULT (UTC) | Creation time |
| `updated_at` | TEXT | NOT NULL DEFAULT (UTC) | Last evidence/status update time |

*Indexes:* `idx_alerts_rule_id`, `idx_alerts_status`, `idx_alerts_source_ip`, `idx_alerts_severity`.

### Table 4: `alert_evidence` (Many-to-Many)
Links alerts to the exact raw events that triggered them (RSD Requirement FR-10).
| Column | Type | Constraints | Description |
|---|---|---|---|
| `alert_id` | INTEGER | NOT NULL, FK -> `alerts(id)` ON DELETE CASCADE | Alert |
| `event_id` | INTEGER | NOT NULL, FK -> `events(id)` ON DELETE CASCADE | Associated event |
| *Primary Key*| - | PRIMARY KEY (`alert_id`, `event_id`) | Composite primary key |

### Table 5: `incidents`
Security analyst investigation cases grouping related alerts.
| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Incident ID |
| `title` | TEXT | NOT NULL | Short incident summary title |
| `description` | TEXT | NOT NULL DEFAULT '' | Detailed investigation notes |
| `status` | TEXT | NOT NULL DEFAULT `open` CHECK in (`open`, `in_progress`, `closed`) | Case lifecycle status |
| `severity` | TEXT | NOT NULL DEFAULT `medium` CHECK in (`low`, `medium`, `high`, `critical`) | Incident severity |
| `created_at` | TEXT | NOT NULL DEFAULT (UTC) | Opening timestamp |
| `updated_at` | TEXT | NOT NULL DEFAULT (UTC) | Last modified timestamp |

### Table 6: `incident_notes`
Append-only audit trail and notes added by SOC analysts during investigation.
| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Note ID |
| `incident_id` | INTEGER | NOT NULL, FK -> `incidents(id)` ON DELETE CASCADE | Incident |
| `author` | TEXT | NOT NULL DEFAULT 'analyst' | SOC analyst username or role |
| `note` | TEXT | NOT NULL | Investigation entry |
| `created_at` | TEXT | NOT NULL DEFAULT (UTC) | Note submission timestamp |

*Join Table:* `incident_alert` (`incident_id`, `alert_id`) links one or more alerts to an incident.

## 3. REST API Specification

Base URL: `http://localhost:5000`  
Standard Response Format:
```json
{
  "ok": true,
  "data": { ... }
}
```
Error Response:
```json
{
  "ok": false,
  "error": "Error description message"
}
```

---

### Ingestion

#### `POST /api/ingest`
Uploads raw SSH authentication log text or file. Automatically hashes the file using SHA-256 to prevent duplicate processing, inserts events into SQLite, and triggers the detection engine.
- **Headers / Body:** 
  - Multipart form upload with `file` field, or
  - Raw body with header `X-Filename: <name>`
  - Optional Query Param: `?year=2026`
- **Response (201 Created):**
```json
{
  "ok": true,
  "data": {
    "log_file_id": 1,
    "filename": "attack_brute_force_10.log",
    "events_stored": 10,
    "malformed_lines": 0,
    "new_alerts": 1,
    "updated_alerts": 0,
    "alert_ids": [1]
  }
}
```
- **Duplicate Upload Response (200 OK):**
```json
{
  "ok": true,
  "data": {
    "duplicate": true,
    "message": "This file has already been uploaded.",
    "log_file": { "id": 1, "filename": "attack_brute_force_10.log", ... }
  }
}
```

#### `GET /api/logs`
Returns list of all uploaded log file records.

### Events (SOC Search & Filtering)

#### `GET /api/events`
Query parameters:
- `source_ip` (string): Filter by IP
- `username` (string): Filter by username
- `outcome` (string): `success` or `failure`
- `event_type` (string): `failed_login`, `accepted_login`, `invalid_user`, etc.
- `since` (string): ISO timestamp lower bound
- `until` (string): ISO timestamp upper bound
- `limit` (int, default 100, max 1000)
- `offset` (int, default 0)
- **Response (200 OK):**
```json
{
  "ok": true,
  "data": {
    "count": 10,
    "events": [
      {
        "id": 1,
        "timestamp": "2026-10-24T14:00:00",
        "host": "web01",
        "username": "deploy",
        "source_ip": "203.0.113.50",
        "port": 41000,
        "method": "password",
        "outcome": "failure",
        "event_type": "failed_login",
        "raw_line": "Oct 24 14:00:00 web01 sshd[5000]: Failed password for deploy..."
      }
    ]
  }
}
```

#### `GET /api/events/<id>`
Returns details for a single raw event by ID.

### Alerts & Evidence

#### `GET /api/alerts`
Query parameters:
- `status`: `new`, `investigating`, `resolved`, `false_positive`
- `severity`: `low`, `medium`, `high`, `critical`
- `rule_id`: `DR-01`, `DR-02`, `DR-03`, `DR-04`, `DR-05`
- `source_ip`: Filter by attacking IP
- `limit`, `offset`
- **Response (200 OK):**
```json
{
  "ok": true,
  "data": {
    "count": 1,
    "alerts": [
      {
        "id": 1,
        "rule_id": "DR-01",
        "rule_name": "SSH brute force",
        "severity": "medium",
        "status": "new",
        "source_ip": "203.0.113.50",
        "first_seen": "2026-10-24T14:00:00",
        "last_seen": "2026-10-24T14:01:48",
        "summary": "10 failed logins from 203.0.113.50 between 2026-10-24 14:00:00 and 2026-10-24 14:01:48",
        "explanation": "SSH brute force (DR-01): 10 failed logins from 203.0.113.50."
      }
    ]
  }
}
```

#### `GET /api/alerts/<id>`
Returns alert details including its linked **evidence events** array.
```json
{
  "ok": true,
  "data": {
    "id": 1,
    "rule_id": "DR-01",
    "severity": "medium",
    "status": "new",
    "source_ip": "203.0.113.50",
    "evidence": [
      {
        "id": 1,
        "timestamp": "2026-10-24T14:00:00",
        "raw_line": "Oct 24 14:00:00 web01 sshd[5000]: Failed password for deploy...",
        "source_ip": "203.0.113.50"
      }
    ]
  }
}
```

#### `PATCH /api/alerts/<id>/status`
Updates triage status.
- **Request Body:**
```json
{ "status": "investigating" }
```
- **Allowed values:** `new`, `investigating`, `resolved`, `false_positive`

### Statistics (SOC Dashboard)

#### `GET /api/statistics`
Provides aggregated metrics in a single query for Sabri's frontend dashboard:
- Total events, accepted logins, failed logins.
- Unique IP count and unique username count.
- Count of alerts grouped by severity (`critical`, `high`, `medium`, `low`).
- Top 10 attacking source IPs by volume.

```json
{
  "ok": true,
  "data": {
    "total": 1500,
    "accepted": 45,
    "failed": 1455,
    "unique_ips": 12,
    "unique_users": 8,
    "total_alerts": 4,
    "alert_counts_by_severity": {
      "critical": 1,
      "high": 1,
      "medium": 2
    },
    "top_source_ips": [
      { "source_ip": "203.0.113.50", "event_count": 120 },
      { "source_ip": "198.51.100.22", "event_count": 45 }
    ]
  }
}
```

### Incidents & Investigation

#### `POST /api/incidents`
Creates an investigation case.
```json
{
  "title": "Brute Force Attack on SSH Gateway",
  "description": "Multiple IPs targeting deploy and root accounts",
  "severity": "high"
}
```

#### `GET /api/incidents`
Lists all incident cases with optional `?status=` filter.

#### `GET /api/incidents/<id>`
Returns complete incident details, including all linked alerts and investigation notes.

#### `PATCH /api/incidents/<id>/status`
Updates status (`open`, `in_progress`, `closed`).

#### `POST /api/incidents/<id>/alerts`
Associates an alert with the incident case.
```json
{ "alert_id": 1 }
```

#### `POST /api/incidents/<id>/notes`
Appends an analyst note to the case history.
```json
{
  "note": "Blocked source subnet 203.0.113.0/24 on perimeter firewall.",
  "author": "adnan"
}
```

#### `GET /api/incidents/<id>/notes`
Fetches chronological notes for an incident.

## 4. Security & Best Practices

1. **SQL Injection Prevention:** Every query in `backend/repository.py` uses DB-API parameterized queries (`?` placeholders). No user inputs are concatenated into SQL strings.
2. **Input Validation:**
   - Integer bounds checking for `limit`, `offset`, and port IDs.
   - Strict whitelisting of statuses (`status IN ('new', 'investigating', 'resolved', 'false_positive')`).
   - Strict whitelisting of severities (`low`, `medium`, `high`, `critical`).
3. **Data Integrity:**
   - Composite unique constraint `UNIQUE(log_file_id, line_hash)` guarantees duplicate log lines within a file are never stored twice.
   - Unique constraint on `file_hash` prevents duplicate file reprocessing.
   - Foreign key cascading deletes clean up child records when an incident or log file is removed.
